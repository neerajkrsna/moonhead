CORE-OS: Yocto + Rust PID 1 Prototype

A focused x86-64 prototype built with the Yocto Project (OpenEmbedded / BitBake), an upstream-supported Linux LTS kernel, and a small Rust PID 1. The first milestone is one reproducible image and a tested service lifecycle; candidate workload profiles, additional architectures, and kernel features are gated on compatibility tests and measured value. Yocto's package format and allarch class do not imply Ubuntu package or command compatibility.

LAYER 3 // YOCTO (meta-coreos) USERLAND
Curated Yocto Userland & One Prototype Image

Core Engineering Mechanism

BitBake builds a pinned, curated glibc userland for one generic x86-64 target. PACKAGE_CLASSES controls Yocto's output package format; it does not provide Ubuntu repository compatibility. Use allarch only for architecture-independent files, not as a binary-compatibility mechanism.

Security and Efficiency Evidence

  • Read-only rootfs and A/B updates are planned milestones; neither is assumed in the first bootable image.
  • Generate an SPDX SBOM for release images; treat CVE reports as triage inputs, not a complete security audit.
  • Build an SDK only when a defined external application-development workflow requires it.

Scrutiny Trade-Off & Constraint

Yocto has a substantial learning curve and clean builds need significant disk and time. Measure this project's build resources; shared sstate-cache helps but does not guarantee minute-scale builds.

Yocto Distro & Image Recipe Snippet

# meta-coreos/conf/distro/coreos.conf DISTRO = "coreos" PACKAGE_CLASSES = "package_deb" VIRTUAL-RUNTIME_init_manager = "coreos-pid1" DISTRO_FEATURES:remove = "systemd sysvinit" DISTRO_FEATURES:append = " usrmerge seccomp" INHERIT += "create-spdx cve-check"

LAYER ARCHITECTURE

Composable Yocto Metadata Layer (meta-coreos)

Keep product policy in meta-coreos, pinned to a supported Yocto release and compatible layer revisions. Start with one QEMU x86-64 machine; add vendor BSP layers only when a physical target is selected.

  • conf/distro/coreos.conf: Selects the init provider using the correct Yocto variable and removes systemd from the target runtime feature set.
  • recipes-core/coreos-pid1/: Installs and tests the Rust init package, including its runtime-provider aliases and /sbin/init path.
  • recipes-images/: Builds one prototype image; packagegroups for candidate workloads are deferred.

Hardware Discovery (Future Work)

The prototype records the machine and available kernel capabilities. It does not automatically write “optimal” global tunables. Any hardware-specific profile must be explicit, reversible, and benchmarked on its target.

# Prototype policy 1. Detect and report CPU, memory, storage, and kernel capabilities. 2. Keep the generic profile unless a tested machine profile is selected. 3. Apply per-service cgroup limits only after workload validation. 4. Do not promise hard real-time behavior from general-purpose Linux.
